- `/deep/nope/path` → HTTP/2 404; `text/html`; `cache-control: max-age=31536000`; `x-cache: Error from cloudfront`; `age: 31562`. Served body is the SPA 404 page (`<title>Page not found | WiSaw…`, canonical → `https://wisaw.com/`).
- `/sitemap.xml` → 200; `application/xml`; length **10,118,891 (~10.1 MB)**; `cache-control: max-age=300`; `last-modified: Sun, 08 Nov 2026 12:04:02 GMT` (same-day fresh); contains **21,988 `<loc>` URLs** — within Google's 50 MB / 50,000-URL per-sitemap limits.
- `/robots.txt` → 200; `text/plain`; **`cache-control: max-age=31536000`**; `server: AmazonS3`.
- `/manifest.json` → 200; `application/json`. `/site.webmanifest` → 200; `application/manifest+json` — but the served HTML references **only `/manifest.json`** (`<link rel="manifest" href="/manifest.json" />`); site.webmanifest is an orphan duplicate (empty `"name"`/`"short_name"`).
- Verdict on "asset-miss as 200 text/html": that failure mode *would* be harmful (a 200 HTML body for a JS/CSS miss is the classic soft-404 pattern — crawlers index it as content, caches store garbage), but **today's live behavior returns a correct 404 status**, so the harm does not currently exist at the status-code level. Residual harm: the 404 error document itself is edge-cacheable for a year (`max-age=31536000` on an error response; observed `age` ≈ 8.8 h), so a URL that 404s once (e.g., a photo page published shortly after Googlebot first hit it) can keep serving 404 from edge error caches long after it goes live.

### Q4. index.html freshness mechanics
- Today's `cache-control: max-age=900` on `/` and `/about` means a crawler can be served an index.html up to **15 minutes** stale (plus any CloudFront TTL), with `x-cache: Hit` + `age: 389` confirming edge caching is active. This is acceptable freshness; the prior year-long staleness regime is gone.
- CloudFront custom error does **not** mask 404s as 200 at the edge today: garbage route and mutated asset both return HTTP 404 (`x-cache: Error from cloudfront`). Caveat: we observe only the CloudFront edge; S3 origin behavior is inferred from `server: AmazonS3` on error responses, not directly probed.
- Real weak spot: **error responses carry `cache-control: max-age=31536000`** with observed ages ~8.8 h — long-lived negative caching of 404 HTML.

### Q5. x-robots-tag / noindex audit; canonical & www-vs-apex
- `x-robots-tag: index, follow` present on `/` and `/about` (positive directive, not a blocker). No `noindex`/`nofollow` anywhere in served HTML (grep count = 0); meta robots is `index, follow, max-image-preview:large, max-snippet:-1, max-video-preview:-1`.
- Canonicals in raw (pre-JS) HTML: `/` → `<link rel="canonical" href="https://wisaw.com/" data-rh="true">`; `/about` → `href="https://wisaw.com/about"` (self-referencing ✓); garbage deep route → `href="https://wisaw.com/"` (homepage-pointing canonical on a 404 — tolerable since status is a true 404). Canonical host = apex, matching all sitemap `<loc>` values (`https://wisaw.com/...`).
- www/apex consolidation: `http://wisaw.com/` → **301** `location: https://wisaw.com/` (`x-cache: Redirect from cloudfront`, server: CloudFront). `https://www.wisaw.com/` → **HTTP/2 301** `location: https://wisaw.com/` (`x-cache: LambdaGeneratedResponse`). Single canonical origin (apex HTTPS) with permanent redirects — strongest consolidation signal per Google's canonical doc; no duplicate-content split between www and apex.

## Leads
- Set CloudFront error-response cache TTL low (e.g., ≤60 s) or strip `max-age=31536000` from the S3 metadata of the custom 404 document; sticky edge 404s can suppress freshly published `/photos/<id>` and `/videos/<id>` pages.
- Fix deployed AASA content-type to `application/json` via S3 object metadata / CloudFront response-header policy (the `_headers` intent proves this was intended but never landed on S3); reconcile the 303-byte well-known copy vs 399-byte root copy.
- Verify against Apple docs (fetch failed here) that legacy `paths` syntax + mismatched app-ID shapes (`com.echowaves` vs `com.echowaves.Wisaw`) in public/apple-app-site-association:6,18,23 are valid for the shipping apps; also probe `/.well-known/assetlinks.json` live (not done — budget).
- Lower robots.txt cache-control from 1 year to minutes/hours.
- Consider deleting or referencing the orphan `/site.webmanifest`; align its empty `name`/`short_name`.
- Sitemap contains `<changefreq>` which Google documents as ignored (build-sitemap doc) — harmless; size 10 MB with max-age=300 is crawlable but a sitemap index + smaller children would be more robust at growth.
- Real hashed-asset cache-control (`/assets/*`) not captured this run — verify it is `immutable` long-TTL (repo intent `_headers:21–22` targets `/static/*`, which CRA/Vite no longer emits).
